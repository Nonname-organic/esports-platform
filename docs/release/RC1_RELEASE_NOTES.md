## 追加機能

| 機能 | 内容 |
|---|---|
| 試合結果の報告と相手の確認 | 対戦チームのオーナー・キャプテンが勝者を報告し、相手チームが確認すると確定する。主催者は即確定できる。Web と Discord Bot が同じ処理を使い、報告は DB に残る（以前は Bot だけが Redis に24時間保持していた） |
| 異議申し立て | 相手チームが報告に異議を出す。主催者が結果の登録で裁定する |
| 試合の再開 | 確定した結果を取り消して進行中に戻す（次の試合が始まっていない場合のみ） |
| 参加の辞退 | 組み合わせの生成前なら、チームのオーナー・キャプテンが参加申請を取り下げられる |
| 利用停止・ロール変更（管理者） | 管理画面でユーザーを停止・再開し、ロールを変える。操作は監査ログに残り、停止したユーザーは次のリクエストから認証を通らない |

## 不具合の修正

- 作成画面で「非公開」「限定公開」を選んでも、一覧・検索・ホームに表示されていた（公開設定が `rules` にしか保存されていなかった）。保存を直し、既存の大会はマイグレーション 028 で補正する
- 「チームを探す」募集（`player_seeks`）の投稿が必ず 500 になっていた（列の長さ不足）。030 で列を広げる
- DB の確定がレスポンス送信の後になっており、登録直後のログインなど続けて行う操作で直前の変更が見えないことがあった
- パスワードの照合（bcrypt）が処理全体を止めていた（同時にログインがあると全リクエストが待たされた）
- タグを付けると、別の入力のラベルが付くことがあった
- 作成・編集画面で、組み合わせを生成できない形式（スイス式・グループステージ・リーグ戦）を選べた。選択肢から外した
- ログアウト時に一部の画面が落ちていた（フックの呼び出し順）
- 5〜10MB の添付ファイルが nginx で 413 になっていた。上限を 11MB に揃えた（画像 5MB・スコアボード OCR 5MB は変わらない）
- 分析イベントの夜間書き出しが、画像用バケットを endpoint なしで使って AWS S3 へ向かい、毎晩失敗していた。専用の設定（`ANALYTICS_EXPORT_BUCKET`）がない限り書き出さない
- 固定日付のテストデータ（Golden）の大会が worker の自動更新で状態を変え、E2E が途中で崩れていた（テストデータの状態を固定）

## セキュリティ

- 他人の大会の試合（開始・スコア・成績・結果・Ban/Pick・OCR）を操作できた。大会の主催者本人と管理者だけに限定した
- 非公開の情報が出ていた。詳細スタッツを非公開にした選手が集計・ランキングに載る、本名が出る、下書き・非公開の大会や非公開の募集がタグ検索・統計・選手履歴に出る、を止めた
- Discord: 連携の OAuth に `state` を導入（なりすまし連携の防止）、Bot にサーバーを作らせる前に Discord 上の管理権限を確認、大会の Discord 設定（サーバー・ロール ID）は主催者・管理者にだけ返す、Webhook の送信先を Discord に限定（SSRF の防止）
- Riot: 他人の選手に Riot ID を連携できた。本人の選手に限定した
- スカウト: 他人のチーム・選手として投稿できた。代理投稿を検証し、入力に上限を設けた
- アップロード: 保存時の拡張子を Content-Type から決める、パストラバーサルの修正、`X-Content-Type-Options: nosniff`、ダウンロード名のヘッダ注入対策
- 認証: ログイン 10回/分・登録 5回/分・パスワード再設定 5回/分を IP 単位で制限（ヘッダの付け替えで回避できない）。パスワードの変更・再設定にも登録時と同じ強度ルール。存在しないユーザーでも照合に同じ時間をかける
- ログ: パスワード再設定メールの本文（リンク）は DEBUG のときだけ出す。メールの宛先はドメインだけ記録する。readiness は内部の例外内容を返さない。設定エラーの文面に入力値（秘密情報）を出さない
- 本番設定の検査: 本番では DB パスワードが空・既定値、`SECRET_KEY` が見本・テスト用の値なら起動しない。デプロイは新しいイメージでこれを先に検査し、不備があれば稼働中のコンテナを入れ替えずに止まる。compose も `DB_PASSWORD` が未設定なら止まる
- Next.js を 15.5.29 に更新し、画像最適化 API を止めた（15.5.27 で未認証の RCE が報告されていた）
- JWT のライブラリを python-jose から PyJWT に変えた（署名方式は HS256 に固定）
- `/metrics` は既定で非公開（ベースコミット 1ddefd7 の変更）

## DB の変更

本番では Deploy の最後（API の readiness が通った後）に `alembic upgrade head` が自動で流れる。
**main へのマージ＝本番への適用**になるので、マージ前にバックアップを取る。

| 版 | 内容 | 既存データへの影響 | 戻し |
|---|---|---|---|
| 028 | 大会の公開設定を `rules` から列へ写す | 列が `public` で `rules` が `limited` / `private` の大会だけを更新。元の値は `tournament_visibility_backup_028` に残す | downgrade 可。適用後に主催者が変えた大会には触れない |
| 029 | `match_result_reports` 表を追加 | なし | downgrade で表を削除（報告の記録は失われる） |
| 030 | `recruitment_posts.post_type` を varchar(10)→(20) | なし（広げるだけ） | `player_seeks` の行が残っている間は downgrade が失敗して元に戻る。先に退避が必要 |

イメージだけを RC1 より前の版に戻しても、旧コードは 030 のスキーマで動く（ローカルで確認済み）。
詳しくは phase10 の「RC1 本番公開の手順」11（ロールバック）を参照。

## 構成の変更

- `docker-compose.prod.yml`: api / worker / scheduler に `REQUIRE_STRONG_SECRETS=true` と `USE_REDIS_QUEUE=true`。postgres の `POSTGRES_PASSWORD` を必須にした（既定値 `esports_pass` を使わない）
- `docker-compose.conoha.yml`: DB 接続数を postgres の上限（`max_connections=20`）に収めた（api 6+6・worker 2+1・scheduler 2+1 = 最大18）
- `nginx/nginx.conf`・`nginx/nginx-tls.conf`: `client_max_body_size` 5m→11m
- `.github/workflows/deploy-demo.yml`: `docker compose up` の前に、新しいイメージで本番設定を検査する
- `frontend/eslint.config.mjs`（新規）: 設定が無く `npm run lint` が対話待ちで止まっていた
- `frontend/playwright.config.ts`: ローカルの並列数を 4 に（CI は 2 のまま）

## 初期公開の範囲

| 区分 | 機能 |
|---|---|
| 提供する | 登録・ログイン、主催者・選手のロール、チーム、大会の作成・管理、エントリー、辞退、シングル／ダブルエリミネーション、ラウンドロビン、結果報告・相手の確認・異議・主催者の確定・試合の再開、スカウト、LFP/LFT、分析・ランキング、通知（画面内）、管理者機能、スコアボード OCR |
| 制限付きで提供する | Match Center（自動更新は 30 秒ごと。WebSocket の即時配信は動いていない）、パスワード再設定メール（SMTP を設定した場合のみ届く） |
| 実 API の確認後に提供する | Discord（OAuth 連携・Bot・Webhook 通知）、Riot（戦績の同期）。設定しなければ無効のまま動く |

## 既知の制限

- Discord・Riot の実 API では未確認（モックによる自動テストのみ）
- Riot ID は自己申告で、Riot 側の確認はしていない（API キーが無い間は戦績の同期も不可）
- Match Center の即時配信: サーバー側の Redis 購読（`redis_pubsub_listener`）が初回コミットから起動されておらず、WebSocket は接続するが更新は届かない。画面は 30 秒ごとの再取得で更新される
- パスワードは先頭 72 バイトまでが有効（bcrypt の仕様。日本語のみなら 24 文字）。登録・ログイン・変更・再設定で扱いは一貫している
- Discord のサーバー権限の確認は、参加サーバーの先頭 200 件まで。Discord のトークン更新は未実装
- 依存関係の既知の指摘: zod（ブラウザ内のフォーム検証だけで使う。サーバー側の検証は Pydantic）、pytest（API イメージに同梱されるが実行されない）
- デスクトップ表示では 1 画面あたり約 12 本のリンク先を先読みする（Next.js の既定）。負荷の観察対象
- E2E は Golden データを前提にしている。tablet（WebKit）プロジェクトはローカルでは実行していない
